# Admin Auth Independence Plan (Section 13)

Date: 2026-09-30. Branch: `infra/lovable-exit-2026-09-30`. Source: `src/components/admin/AdminLoginScreen.tsx`,
`src/integrations/lovable/index.ts`, `src/hooks/useAdminAuth.ts`, and a diff against the unmerged
`rebrand/localdominate-2.0-foundation` branch, which already contains the target implementation.

## 13.1 Current flow (traced from code, `main` / this branch)

```
Google  →  @lovable.dev/cloud-auth-js (createLovableAuth)  →  lovableAuth.signInWithOAuth("google")
        →  Lovable's own OAuth backend performs the Google exchange
        →  returns { tokens }  (a Supabase-compatible session)
        →  supabase.auth.setSession(result.tokens)  — sets the session directly on THIS project's
           Supabase client
        →  Admin app
```

Two admin login paths exist side by side:
- **Email/password** (`onLogin` prop → `useAdminAuth.signIn()` → `supabase.auth.signInWithPassword()`)
  — already **fully independent of Lovable**, native Supabase Auth.
- **"Sign in with Google"** — the Lovable-dependent path. `src/integrations/lovable/index.ts` is marked
  `// This file is auto-generated by Lovable. Do not modify it.` and wraps `@lovable.dev/cloud-auth-js`.
  Lovable performs the actual Google OAuth handshake and hands back tokens that get set on the Supabase
  session — meaning **Lovable, not Google directly, is the OAuth provider from Supabase Auth's point of
  view**. This only works because the current Supabase project (`minijgyozgjuhqgkmilj`) trusts whatever
  `setSession()` is given; it is not a documented, portable OAuth provider configuration.

## 13.2 Admin identification (independent of the Google-vs-Lovable question)

`useAdminAuth.ts`: after any successful sign-in (either path), `checkAdminRole(userId)` queries
`user_roles` for a row with `role = 'admin'` for that user. `isAdmin` gates the admin UI client-side.
This logic is **already fully portable** — it's a plain `supabase.from('user_roles').select(...)` call
with no Lovable involvement, and depends only on the `user_roles` table + `app_role` enum already
inventoried in `SUPABASE_MIGRATION_INVENTORY.md` §7.3–7.4. Note this is **client-side gating only** — no
server-side RLS check was found restricting *which pages load*, only RLS on the data those pages query
(the `has_role()` function backs table-level RLS, e.g. the `customer-uploads` storage policy in
§7.8, separately from this client-side `isAdmin` flag). Worth flagging as a hardening item, not a
migration blocker: an authenticated non-admin user's browser could still load the admin route's JS, it
would just fail to fetch admin-gated data.

## 13.3 Where Lovable participates — precisely

Lovable participates in exactly one place: brokering the Google OAuth handshake for the admin "Sign in
with Google" button. It does not participate in:
- Email/password admin login (native already)
- Admin role determination (native already, `user_roles` table)
- Any customer-facing flow (customers never authenticate — `customers` rows are created by the Stripe
  webhook via service role, no login involved)

## 13.4 Target flow — already built, on `rebrand/localdominate-2.0-foundation`, unmerged

```
Google OAuth  →  Supabase Auth (native, provider configured in the target project's Auth settings)
              →  supabase.auth.signInWithOAuth({ provider: 'google', options: { redirectTo: origin } })
              →  browser redirect to Google  →  Google redirects back to Supabase's own callback URL
              →  Supabase sets the session itself (no manual setSession() call needed)
              →  Admin app  →  checkAdminRole() (unchanged)
```

Diff already on the rebrand branch (verified this session, not re-implemented):
- `src/components/admin/AdminLoginScreen.tsx`: replaces `import { lovable } from '@/integrations/lovable/index'`
  with `import { supabase } from '@/integrations/supabase/client'`, and
  `lovable.auth.signInWithOAuth("google", { redirect_uri: ... })` with
  `supabase.auth.signInWithOAuth({ provider: 'google', options: { redirectTo: ... } })`.
- `src/integrations/lovable/index.ts` — **deleted** on that branch.
- `src/integrations/supabase/previewAuthStorage.ts` — also removed on that branch (per
  `LOVABLE_FINAL_DEPENDENCY_GRAPH.md` §6, this file is a harmless Lovable-preview-iframe fallback that
  degrades to `localStorage` outside Lovable anyway, so removing it is safe cleanup, not a required fix).

## 13.5 Callbacks / redirect URLs

Supabase's native `signInWithOAuth` uses Supabase's own hosted callback URL
(`https://<project-ref>.supabase.co/auth/v1/callback`) registered with Google, then redirects the
browser back to `options.redirectTo` (currently `window.location.origin`, i.e. the site root) after the
session is set. **This means the new project's Auth settings need:**
1. Google OAuth provider enabled, with a Client ID + Client Secret from Google Cloud Console (dashboard-
   only on both sides — not portable via code or migration script).
2. Google Cloud Console's OAuth consent screen / credentials updated to add the **new** project's
   Supabase callback URL as an authorized redirect URI (it currently only knows the old project's
   callback URL, or possibly Lovable's own broker URL — unverified which, since Lovable's exact OAuth
   client configuration is not visible from this repo).
3. `localdominate.org` (and any preview/staging domain in use) added as an authorized JavaScript origin.

## 13.6 Session handling

Native Supabase Auth session handling (`onAuthStateChange`, `getSession()`) is already what
`useAdminAuth.ts` uses — this does not change between old and new project, only the project URL/key the
`supabase` client points at (see `ENVIRONMENT_VARIABLE_MATRIX.md`).

## 13.7 Protected routes / authorization logic

Client-side only, as noted in §13.2: `useAdminAuth().isAdmin` gates rendering, not RLS. Which routes use
it: `Admin.tsx`, `Analytics.tsx`, `ABTestDashboard.tsx`, `InternalLinkingDashboard.tsx`,
`ConversionOptimizationReport.tsx`, `ContentUpdateCalendar.tsx` (confirmed via grep for
`useAdminAuth`/`has_role` references in `src/pages/`). This logic itself needs no migration change — only
the underlying Supabase project it talks to.

## 13.8 Environment variables

None specific to auth beyond the three already-inventoried `VITE_SUPABASE_*` vars (see
`ENVIRONMENT_VARIABLE_MATRIX.md`) — Google OAuth client ID/secret are configured server-side in the
Supabase dashboard, not as app env vars, so there's nothing to add to `.env.example` for this.

## 13.9 Migration requirements (ordered)

1. Port the `rebrand/localdominate-2.0-foundation` diff (§13.4) onto this branch or onto `main` at
   cutover time — **not before**, since it changes runtime auth behavior and this migration explicitly
   must not touch `main` yet.
2. Create the Google OAuth client credentials (or reuse existing ones if Markus/Re already has a Google
   Cloud project for this) and register the new project's Supabase callback URL.
3. Enable the Google provider in the new Supabase project's Auth settings with those credentials.
4. Test: a real admin Google sign-in against the new project, followed by a `checkAdminRole()` check
   succeeding for that user's `user_roles` row (which must have been migrated per `DATA_MIGRATION_PLAN.md`
   before this test can pass end-to-end).

## 13.10 Explicit non-goal

**Do not weaken admin authorization during migration.** Nothing above changes who can log in as admin or
what `isAdmin` means — it only changes which OAuth broker sits between Google and Supabase. The
client-side-only route gating noted in §13.2/§13.7 is a pre-existing condition, flagged for awareness,
not something this migration should either fix or accidentally loosen further.
